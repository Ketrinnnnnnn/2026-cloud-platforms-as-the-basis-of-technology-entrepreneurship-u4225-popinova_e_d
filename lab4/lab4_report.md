\## Цель работы



Создать прототип AI-приложения с базовой функциональностью и обосновать выбор инфраструктурных ресурсов для трёх стадий развития проекта.



\## Описание продукта



В качестве MVP выбрано \*\*AI-приложение для интеллектуального анализа изображений\*\*. Пользователь загружает фотографию через веб-интерфейс, система отправляет её в LLM (большую языковую модель), которая генерирует текстовое описание или классификацию. 



\*\*Ключевые компоненты инфраструктуры:\*\*

\- \*\*Cloud Run (Web)\*\*: веб-интерфейс и API для приема запросов.

\- \*\*Cloud Run (Worker)\*\*: воркеры для асинхронной обработки изображений.

\- \*\*Cloud Tasks\*\*: очередь задач для распределения нагрузки.

\- \*\*Vertex AI (LLM)\*\*: модель для анализа изображений (оплата за токены).

\- \*\*Cloud Storage\*\*: хранение исходных и обработанных изображений.

\- \*\*Firestore\*\*: база данных для метаданных пользователей и задач.

\- \*\*Artifact Registry \& Cloud Build\*\*: CI/CD и хранение Docker-образов.

\*\*Архитектурные решения:\*\* Добавление очереди Cloud Tasks для сглаживания пиков. Увеличение лимитов воркеров (до 40 инстансов). Стейджинг-среда (Staging) для тестирования обновлений перед выкаткой партнёрам.

!\[Продакшн](images/production.drawio.png)

\## Обоснование выбора ресурсов



1\. \*\*Почему Cloud Run, а не GKE (Kubernetes)?\*\*

&#x20;  На начальном этапе и этапе тестирования Kubernetes (GKE) избыточен. Он требует наличия минимум одного всегда работающего узла (ноды), что стоит денег даже при нулевой нагрузке. Cloud Run идеально подходит для MVP, так как масштабируется до нуля.

2\. \*\*Почему Cloud Tasks?\*\*

&#x20;  При росте до 20 000 пользователей синхронная обработка изображений приведёт к таймаутам. Cloud Tasks позволяет выстроить асинхронную очередь: API быстро принимает запрос и отдаёт ответ пользователю, а обработка изображения происходит в фоне (Worker'ами).

3\. \*\*Почему Firestore, а не Cloud SQL?\*\*

&#x20;  Для хранения метаданных (кто отправил, статус задачи) NoSQL база Firestore работает быстрее и дешевле, чем реляционная Cloud SQL на начальных этапах. Она также отлично интегрируется с Cloud Run.

4\. \*\*Почему выделен Vertex AI?\*\*

&#x20;  Вместо развертывания собственной ML-модели на GPU (что стоило бы тысячи долларов в месяц за аренду железа), мы используем API Vertex AI. Мы платим только за токены. Это позволяет сохранять низкий порог входа (в MVP стадии расходы на AI составляют всего $1.84).

\## Выводы



1\. \*\*Начальный этап\*\* является экономически безопасным: полная стоимость владения (TCO) не превышает $34 в месяц благодаря serverless-архитектуре и оплате за токены.

2\. \*\*Этап тестирования\*\* требует вложений в стабильность (стейджинг) и асинхронность, но стоимость на 1 задачу снижается с $0.0038 до $0.0032 за счёт эффекта масштаба.

3\. \*\*Продакшн\*\* показывает, что более 70% бюджета уходит на оплату AI-токенов и работу воркеров. Именно на этих статьях необходимо сосредоточить оптимизацию (кэширование результатов, сжатие изображений перед отправкой в модель).

4\. \*\*Анализ чувствительности\*\* показал, что главный риск — это рост потребления AI-токенов. Для продакшна необходимо внедрить жёсткие лимиты на количество запросов от одного пользователя.
